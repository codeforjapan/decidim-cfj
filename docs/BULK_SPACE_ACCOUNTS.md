# 参加スペース単位のアカウント一括発行

参加スペース（Assembly）ごとに、匿名IDの確定アカウントを一括発行する仕組みです。
研修・ワークショップや学校現場などで、参加者にスムーズに Decidim 上で活動してもらうために、運営側でアカウントを一括登録して配布する運用を想定しています。
特に学校現場など、**参加者の実メールアドレスを収集しない**運用に対応しています。
汎用の一括登録（`docs/BULK_USER_IMPORT.md`）を土台に、ID の自動採番とスペースへの登録・権限割り当てを重ねたものです。

構成ファイル

| ファイル | 役割 |
|----------|------|
| `app/services/decidim/bulk_space_account_issuer.rb` | 採番・発行のコアロジック（`BulkUserImporter` を内部で使用） |
| `app/models/decidim/bulk_user_import_setting.rb` | 組織ごとの設定（有効フラグ・ダミーメールのドメイン） |
| `lib/tasks/bulk_users.rake` | `bulk_users:issue` / `bulk_users:configure` |
| `app/controllers/decidim/system/bulk_user_import_settings_controller.rb` | /system の設定画面 |
| `app/controllers/decidim/assemblies/admin/bulk_account_issues_controller.rb` | アセンブリ管理画面の発行UI |
| `app/permissions/decidim/bulk_account_issue_permissions.rb` | 発行UIの権限（組織admin限定） |
| `config/initializers/bulk_account_issuing.rb` | ルーティング・メニュー・管理ログ表示の登録 |
| `config/locales/bulk_account_issue.{ja,en}.yml` | 画面文言 |

## 1. 前提となる運用

- メールアドレスはダミー（実在しないドメイン）で発行します。参加者はメールを受信できません
- パスワードを忘れた参加者には、発行時に多めに作っておいた**予備アカウント**を渡します。再発行の仕組みはありません（メール経由のリセットも使えません）
- 予備と通常のアカウントに区別はありません。単に必要数より多めに発行してください
- 出力CSVは予備分を配り終えるまで参照する**運用資産**です。配布が終わったら削除してください

## 2. 事前設定（組織ごと）

発行には組織ごとの設定（有効フラグとダミーメールのドメイン）が必要です。
**/system（大元の管理画面）の「一括アカウント発行」ページ**から組織ごとに設定できます。rake でも設定できます。

```bash
DECIDIM_ORGANIZATION_ID=1 bundle exec rails bulk_users:configure ENABLED=true EMAIL_DOMAIN=chiba-mirai.test
DECIDIM_ORGANIZATION_ID=1 bundle exec rails bulk_users:configure   # 現在値の表示
```

`EMAIL_DOMAIN` の決め方:

- **形式**: 小文字英数字と `.` `-` のみ。**`chiba-mirai.test` のようにドット付き（TLD 相当を含む）が必須**です
  （ドットなしだと発行はできてもログイン画面のメール形式チェックで弾かれ、参加者がログインできません。設定の保存時にも拒否されます）
- **推奨 TLD は `.test`**: RFC 2606 で予約されておりグローバル DNS には委任されない（＝絶対に実在・配送されない）うえ、短くて打ちやすいためです。
  `.example` / `.invalid`（同じく RFC 2606 予約）や `.internal`（ICANN がプライベート用途向けに予約）でも技術的には同等です
- **自作 TLD（`.xx` など）は不可**: 将来 gTLD として実在してしまう可能性があり、実在アドレスとの衝突・誤配送のリスクがあります
- ログインID（メール形式）の一部として参加者に配布されるので、全体として**短く打ちやすい**文字列にしてください

組織の利用規約バージョン（`tos_version`）が未設定の場合は実行できません（`BULK_USER_IMPORT.md` 2.1 を参照）。

## 3. 入力CSV

1行が「どのスペースに・どの権限で・何人分」という**生成指示**です。アカウントごとの行は書きません。

```csv
space_type,space_slug,role,count
assemblies,a-high,participant,40
assemblies,a-high,admin,3
assemblies,b-junior,participant,25
```

| 列 | 内容 |
|----|------|
| `space_type` | 当面 `assemblies` のみ |
| `space_slug` | 参加スペースの slug（URL の `/assemblies/○○` の部分）。**15文字まで** |
| `role` | `participant`（一般参加者）または `admin`（参加スペース管理者）。空欄は `participant` |
| `count` | 発行する件数。予備分を含めた数を書く |

指示に1件でも不正（未知の slug・15文字超・未知の role など）があると、**何も作らずに** exit 1 で止まります。

## 4. 実行

### 4.1 管理画面から（非公開アセンブリ単位）

組織の設定が有効で、かつアセンブリが**非公開（プライベート参加スペース）**のとき、そのアセンブリの管理画面サイドメニューに「アカウント一括発行」が表示されます（組織の admin のみ）。

- スペースは画面の文脈から確定するため、入力は「参加者数」「管理者数」の2つだけです
- 画面には次に採番されるID（例: `a-high-013` / `a-high-a002`）が表示されます
- 同期処理のため **1回の発行は合計100件まで**です。超える場合は複数回に分けるか、rake を使ってください
- 発行が終わると認証情報（パスワード・フリガナ）を含む結果CSVのダウンロードが始まります
- 実行は管理ログに記録されます（誰が・どのスペースに・何件）

### 4.2 rake から（複数スペースまとめて）

```bash
# 採番と生成されるIDの事前確認（何も作成しない）
DECIDIM_ORGANIZATION_ID=1 bundle exec rails bulk_users:issue IN=tmp/bulk/plan.csv DRY_RUN=1

# 実行
DECIDIM_ORGANIZATION_ID=1 bundle exec rails bulk_users:issue IN=tmp/bulk/plan.csv
```

出力CSV（既定 `tmp/bulk_users/issued_accounts_<日時>.csv`、パーミッション 0600）:

```
space_slug,role,account_id,email,password,furigana,status,error
a-high,participant,a-high-001,a-high-001@chiba-mirai.test,K7M2WX4NPR,ケー・ナナ・エム・ニ・ダブリュー・エックス・ヨン・エヌ・ピー・アール,created,
```

- 1件処理するたびに書き出してフラッシュします。途中でプロセスが落ちても処理済み分の認証情報は残ります
- 既存の出力ファイルには書き込みません（上書きすると発行済みパスワードが失われるため、存在する場合は中断します）
- `furigana` 列は読み上げ・紙面配布用のカタカナ読みです。**平文パスワードと同じ機密度**で扱ってください

## 5. 生成規則

### アカウントID

ID・表示名・メールのローカル部・nickname はすべて同一の文字列です。

| 権限 | 形式 | 例 |
|------|------|----|
| 参加者 | `<slug>-<連番3桁>` | `a-high-001` |
| 管理者 | `<slug>-a<連番3桁>` | `a-high-a001` |

- 連番は権限ごとに独立で、**既存の同形式IDの最大値の次**から始まります。再実行すると続きから追加されます
- 採番は**組織内の nickname の走査**で決まります。スラッグ接頭辞ごとに完全に独立なので、別スペースでの発行は他のスペースの連番に影響しません
- **スペースのメンバー一覧から削除しても番号は戻りません。** メンバー一覧からの削除はスペース所属を外すだけで、アカウント本体（と nickname）は残るためです。番号が解放されるのは、アカウント自体が抹消されて nickname が空になった場合だけです
- 失敗した行の番号は欠番になり、再利用しません
- Decidim の nickname は20文字上限のため、slug は15文字までです。超える場合は slug 自体を短くしてください（切り詰めによる別スペースとの衝突を避けるため、自動では切りません）
- slug に大文字が含まれる場合、ID は小文字化されます（nickname は小文字のみのため）

### パスワード

大文字英字と数字から、紛らわしい文字を除いた **29文字・10桁**（約48.6bit）です。記号は使わず、ハイフンやスペースなどの区切り文字も入れません（例: `K7P2M9XTB4`）。

```
23456789ABCDEFGHJKMNPRSTVWXYZ
（0・O、1・I・L、U・V の組から 0 O 1 I L U を除外 ─ 誤読の温床になるため。
　Q は読み上げで 9（キュウ）と紛れるため除外）
```

記号を使わないのは、JIS/US 配列の差、全角文字の混入、`\` と `¥` の表示揺れを避けるためです。

**パスワードは大文字で入力する必要があります。** 小文字で入力するとログインに失敗し、20回失敗するとアカウントが1時間ロックされます。配布物とログイン案内に「大文字で入力」と明記してください。

## 6. スペースへの登録と権限

1回の発行で、ユーザー作成とスペースへの登録がまとめて行われます。

| role | ユーザー作成 | プライベートユーザー登録 | AssemblyUserRole | スペースをフォロー |
|------|:---:|:---:|:---:|:---:|
| `participant` | ○ | ○（非公開スペースの場合） | ─ | ─ |
| `admin` | ○ | ○（非公開スペースの場合） | ○（role: admin） | ○ |

**管理者にもプライベートユーザー登録を行うのがポイントです。** `AssemblyUserRole` は管理画面へのアクセス権であって参加権ではなく、Decidim の `can_participate?` はプライベートユーザー登録しか見ません。登録しないと「管理者なのに自分のスペースに入れない」状態になります（組織全体の管理者ですら入れません）。

- プライベートユーザーは `published: false` で登録します。スペースの公開メンバー一覧には載りません（参加可否には影響しません）
- ユーザー作成とスペース登録は1アカウントずつトランザクションで束ねています。途中で失敗した場合はそのアカウントごと巻き戻り、「ユーザーだけ作られてスペースに入れない」状態は残りません
- 既存の管理者追加フローと違い、招待メール・通知は送られません

## 7. 運用上の注意

- **スペースを非公開にするには `private_space` だけでは足りません。** `is_transparent`（透明性）が ON のままだと、未ログインの第三者にもスペースの中身が見えます（参加はできません）。児童生徒の投稿を扱う場合は必ず OFF にしてください
- 作成されたアカウントは通知メール・ニュースレターがすべて OFF です（ダミーアドレスへの送信はバウンスとして蓄積し、メール基盤全体を止めかねないため）
- **参加スペース管理者は、管理画面に初めて入るときに管理者向け利用規約への同意を求められます。** これは本人が同意すべきものとして、運営側では設定しません
- プロフィールページ（`/profiles/<ID>`）は未ログインでも閲覧できます。IDが匿名なので個人は特定されませんが、この仕組みの外で氏名入りのアカウントを作らないでください

## 8. テスト運用（本番導入前のトライアル）

導入前に「一度発行して様子を見たい」場合は、**本番用とは別スラッグのダミースペースで試してください**。
採番はスラッグ接頭辞ごとに独立なので、ダミースペースで何件発行しても、本番スペースの連番は必ず 001 から始まります。

推奨手順:

1. テスト用の非公開アセンブリを作る（例: slug `trial-x`。`private_space` ON・`is_transparent` OFF）
2. 少数（2〜3件）だけ発行し、ログイン・参加・管理画面を確認する
3. 確認が終わったらテスト用スペースを非公開のまま削除し、結果CSVを破棄する

注意点:

- **メンバー一覧からの削除はアカウント削除ではありません。** スペース所属が外れるだけで、アカウントはログイン可能なまま組織に残り、連番も戻りません（§5 参照）
- テストで作ったアカウントは組織に残り続けます。発行済みアカウントを一括で抹消する手段は現状ありません（§9 参照）。残留アカウントを最小にするため、**テスト発行は必要最小限の件数**にしてください
- 同じスペースで「テスト後に 001 から発行し直す」ことは現状できません。連番を最初から始めたい場合は、スラッグを変えた新しいスペースを使ってください

## 9. 既知の制約

- 対象は Assembly のみです（participatory_processes は将来対応の構造だけ用意しています）
- 発行済みアカウントの一覧・削除の専用手段はありません。管理画面の参加者一覧で ID 形式（`<slug>-` 前置）を検索してください。スペースのメンバー一覧から削除してもアカウント本体は残り、ログインも可能なままです
- 途中でプロセスが落ちた場合、出力済みの行までは有効です。再実行は**指示の `count` ぶんを新たに追加**します（残数だけ作る動きではありません）。続きを発行する場合は `count` を残数に書き換えてから再実行してください
